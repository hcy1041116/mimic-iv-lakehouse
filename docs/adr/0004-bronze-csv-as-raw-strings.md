# 0004 Bronze 把 CSV 存成每欄的原始字串

- 狀態：accepted（2026-11-26）

Bronze 要「原樣」保存來源（10 月定案的原則）。CSV 的原樣有兩種做法：整行存成一個字串，或是照表頭拆成欄位、每欄都存成字串。我們選後者，另外加一欄 `_corrupt_record`，格子數不對的行把整行原文放在這裡。判斷依據是課程第 38 課的原則：「不能信任來源會照標準給資料時，先用 text 存下原文」。MIMIC 是官方發布的匯出檔，格式可信（`admissions` 沒有引號、行數 = 筆數 + 1），髒的是內容，例如語言填 `?`、劑量填 `1-2`。內容髒不會讓拆欄位出錯。

## 考慮過的選項

- **整行存原文**（前身存原始 JSON 字串的做法，課程第 38 課）：逐字相同，來源多一欄也寫得進去；但 Bronze 不能直接查，格子裡有換行時會把一筆拆成兩行。
- **在 Bronze 就轉型別**（課程第 42 課）：查起來最方便；但轉不過去的值（例如 `2150-13-40`）會變成 null，原本寫了什麼就找不回來，Silver 的品質規則也沒有證據可記。

## 後果

- 欄位名照表頭，全部是字串，型別到 Silver 才轉。空白的格子會變成 null（本機實測）。
- 格子太少或太多的行都會落地：太少時缺的欄位是 null，太多時多出的值會丟掉，兩種情況整行原文都在 `_corrupt_record`（本機實測，`tests/test_bronze.py`）。
- 不存行號。版本比較用不到行號：同一位病人的多次住院比 `admittime`，同一筆資料的多個版本比批次序號。追查來源靠 `_source_file` 和業務鍵。
- 存成 Delta 表，不建 view。view 每次都重讀檔案，Volume 裡的檔案一換，Bronze 就跟著變。
- 同一批重跑時，只取代那一批（Delta `replaceWhere`），Bronze 的筆數才能每次都等於來源行數減掉表頭。
- 之後加的表如果格子裡有換行，要重新檢查這個決定。
