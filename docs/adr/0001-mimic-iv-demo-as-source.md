# 0001 資料來源用 MIMIC-IV 展示版的醫院資料表

- 狀態：accepted（2026-11-26）

前身 `fhir-lakehouse` 用 Synthea 產生 FHIR 資料，卡在三件事：Synthea 不是 FHIR 伺服器，版本、更新時間、增量都要另外寫模擬器去假造；資料太乾淨，error 級的品質規則全部是 0 筆；台灣醫院做資料工程，實際的起點是醫院系統（HIS）的資料表，不是 FHIR。所以這個專案改用 MIMIC-IV Clinical Database Demo 2.2 的 `hosp` 資料表當來源。它是美國一家教學醫院去識別化後的真實病歷，以醫院系統匯出的關聯式表發布，100 位病人，ODbL 開放授權，不用申請。同一批病人有官方轉好的 MIMIC-IV on FHIR Demo 2.1.0，之後做「醫院資料表 → FHIR」時拿來對答案。實測結果見 [mimic-demo-findings.md](../mimic-demo-findings.md)。

## 考慮過的選項

- **維持 Synthea FHIR**：資料量大（1000 多人），但上面三個問題都還在。
- **MIMIC-IV on FHIR 展示版當主來源**：管線設計幾乎不用改，資料也是真的；但起點仍是 FHIR，和台灣的實際情況對不上，而且 `meta` 一樣沒有 `lastUpdated`。改為「對答案」用。
- **OpenMRS 展示資料**：表結構是真的醫院系統，約 5,000 人；但資料是示範用的，還要把整套系統架起來才能產生異動。
- **健保申報 XML**：台灣在地，格式公開；但沒有資料，要自己產，而且是申報資料，不是臨床資料。

## 後果

- **只用展示版。** 完整版（約 30 萬人）要 PhysioNet 認證，它的資料使用協議禁止把資料傳給第三方，包括 API 和線上平台（PhysioNet 2025 年的說明）。所以完整版不放上 Databricks Free Edition，也不能給 agent 讀。展示版公開，面試官可以自己下載重跑。
- **只有 100 人。** 檢驗有 10 萬多筆，夠用來展示管線；但看不出效能問題。用 Spark 和 Databricks 是為了展示目標職缺要的技能，設計上要能放大到完整版的規模。
- **版本和時間是資料本來就有的，不用模擬。** 同一位病人每次住院都記一次婚姻、種族、保險，值會變；檢驗有採檢時間 `charttime` 和結果存入時間 `storetime`。增量怎麼切批次之後再決定。
- **日期被平移到 2110–2201 年，每位病人平移的量不同。** 「日期不能在未來」這類規則不適用；跨病人比較日曆時間沒有意義。
- **前身的決定不直接沿用。** 原樣保存並記錄出處、reject 表分 error／warn、先檢查品質再選最新版本、用來源的 id 當鍵、邏輯表名加各環境 config、Spark 時區固定 UTC、Silver 依版本 MERGE 而 Gold 全量重建：這些概念預計保留。每一項要等用到時，依新資料重新確認，再寫成本專案的 ADR。細節可以參考 `~/projects/fhir-lakehouse/docs/adr/`。前身的 0002（Synthea 產資料）和 0009（匯出模擬器）不再適用。
- **平台**：開發在本機（pytest 加本機 Spark），驗收在 Databricks Free Edition。資料從本機上傳到 Volume。
